## 한 줄 결론

PRD는 3원칙을 **선언**(§3)하고 포지셔닝(§36)까지 정확히 서술했지만, 그 원칙을 **강제하는 요구·수용 기준·런타임 계약이 비어 있다.** 현재 문서대로 구현하면 7개 앱 모두 자기 DoD(§30)를 통과하면서도 (1) 대화 표면이 어디에 어떻게 배선되는지 미정이고, (2) ANA가 상태를 바꿔도 화면이 갱신될 근거가 없으며, (3) 앱 코드를 바꾸는 능력이 한 번도 검증되지 않는다. 즉 §36이 부정한 "지도 달린 챗봇"이 되어도 PRD 위반이 아니다. 세 critical은 각각 이 셋에 대응한다.

## Critical

### ANA-001 — 상태 변경 전파 계약 부재 (§12, B3)

§12의 `app.version: "0.1.0"`은 앱 시맨틱 버전이지 베이스가 요구하는 **변경마다 +1 되는 동기화 카운터**가 아니다. 이름이 같아 구현자가 계약 충족으로 오인하기 쉽다는 점이 더 위험하다. 폴링(약 2.5초)·다기기 동기화 요구도 문서 전체에 없어, ANA가 `state.json`을 수정해도 Watch 표면이 그것을 반영할 근거가 없다. 그 결과 7개 앱 전부의 "ANA can alter …" 수용 기준이 화면에서 검증 불가능해진다.
→ `stateVersion` 같은 별도 최상위 필드 신설 + 폴링/동기화 공통 FR 추가. (`prd-structure-auditor`와 상태 모델 중복 확인 필요)

### ANA-002 — Converse Surface 배선 요구 전무 (§8.1, B2)

베이스 런타임은 대시보드 + 채널 + 대시보드 서버(정적 서빙 · 채팅 브리지 API · 상태 JSON) + 인바운드 릴레이 + 코딩 에이전트이며, "인바운드는 채널로 자동 푸시, 응답은 대시보드로(제안→승인)"가 핵심 규칙이다. PRD는 `index.html / app.js / server.js / state.json` 파일명만 나열하고 **server.js의 책임도, 사용자 발화가 에이전트에 도달하는 경로도, 응답이 화면으로 돌아오는 경로도 정의하지 않는다.** 구현자는 "대화는 Claude Code 터미널에서"로 처리하게 되고, §3.1과 §36이 동시에 무너진다.
→ §8에 배선 절 신설. fakechat 등을 미채택할 경우 그 사실과 대체 수단을 명시(암묵적 누락 ≠ 의도적 단순화).

### ANA-003 — 코드 재작성의 판정 기준이 어떤 수용 기준에도 없음 (§30, B1-2)

앱별 마지막 수용 기준 중 일부는 `alter decision logic`(§18.7), `modify network assumptions`(§19.7), `alter default search behavior`(§20.6)처럼 동작·로직 수준의 단어를 쓴다. 문제는 수준이 낮다는 것이 아니라 **7개 문장 어디에도 "무엇을 어디까지 바꿔야 통과인지"가 없어 전부 가중치·조건·파라미터 편집만으로 충족했다고 주장할 수 있다**는 점이다. §30 DoD 4항의 "state **or** behavior"는 그 주장을 문서 차원에서 승인해 준다. 결과적으로 원칙 2의 핵심인 "앱 코드 재작성 경로"를 한 줄도 구현하지 않고 7개 앱 전부가 자기 DoD를 통과할 수 있다.
→ DoD에 우회 불가 항목 추가 + 앱별 수용 기준에 "코드/기능 진화" 1줄씩 추가.
*(근거 문구는 라운드 1 중 구조 축의 정정 지적을 반영해 "상태 수준에 머문다"에서 위 형태로 조정했다.)*

**ANA-007 (gis) — 검증 완료, 권고 강화**

gis가 표준 모듈만 쓰는 `server.js` PoC(Node 24.13.1, 65행, npm 의존성 0)를 실제로 작성해 4개 기능을 전부 통과시켰다 — 정적 서빙(경로 이탈 3종 차단), `state.json` GET/PUT(temp write + `rename` 원자적 교체), allowlist 프록시(overpass-api.de·earth-search.aws.element84.com 실제 질의 성공, 미허용 호스트 403), Python 워커 `spawn`(stdin/stdout JSON, 실패 시 502 전파). **실현 가능하므로 문안을 완화하지 않고 아래 3개 단서로 강화했다.**

1. **Node 최소 버전 명시**(>= 20 LTS) — 전역 `fetch`가 없으면 프록시를 위해 undici 같은 npm 의존성이 되돌아온다. GIS-007(§30 DoD 런타임 버전 누락)과 같은 수정 지점.
2. **hand-rolled 서버의 안전 요구 명시** — PoC 초판이 404 하나에 크래시하고 에러에 절대 경로를 노출했다. 프레임워크가 기본 제공하던 것이므로 (i) 헤더 전송 후 예외 처리, (ii) 내부 경로·스택 비노출 에러 매핑, (iii) 경로 이탈 검사를 명시적 요구로 넣어야 "의존성 0"이 실제 안전으로 이어진다. *"의존성 0은 비용 제거가 아니라 비용의 이동"이라는 사실을 문안에 남기는 것이 정직하다.*
3. **vendored의 범위 정의** — Turf.js는 단일 UMD 번들이면 되지만 Leaflet은 `leaflet.css`가 `images/marker-icon.png` 등을 상대 경로로 참조해 dist 디렉터리 통째 벤더링이 필요하다. **특히 이 제약이 GIS-001(App 6 래스터 표시)의 해법을 사실상 결정한다** — georaster-layer-for-leaflet은 벤더링 부담이 크고, STAC thumbnail + `L.imageOverlay`는 추가 벤더링이 0. → 리포터는 ANA-007과 GIS-001을 함께 묶을 것.

또한 gis는 이 검증으로 GIS-023(외부 호출을 브라우저 직접 vs 프록시 중 무엇으로 할지 미정)의 confidence를 medium → high로 올렸다. ANA-007(코어는 stdlib)과 GIS-023(외부 호출은 프록시 경유)은 서로를 강화한다 — 프록시가 있어야 §27.2/§27.3, 스로틀(GIS-003), 캐시(GIS-022), provenance(§28)를 한 지점에 모을 수 있다.

**역방향 질의 — gis 실측 회신 완료, 두 권고에 반영됨**

**Q1 → ANA-001: 결과 컬렉션을 분리하라. 2,000 피처 통짜 폴링은 성립하지 않는다.**

| 구성 | compact | 사람 가독 | 2.5초 폴링 | 유휴 시간당 |
|---|---:|---:|---:|---:|
| 포인트 500개 | 229 KB | 365 KB | 1.1 Mbps | 514 MB |
| 포인트 2,000개 | 914 KB | 1,460 KB | 4.6 Mbps | 2,054 MB |
| 폴리곤 2,000개(정점 40) | 2,440 KB | 3,904 KB | 12.2 Mbps | 5,490 MB |
| 레이어 10개 참조만 | — | 2.4 KB | 0.008 Mbps | 3.4 MB |

§16.3 프리셋의 park·parking과 §18의 residential이 전부 폴리곤이라 상한 시나리오가 현실적이다. **다만 대역폭보다 결정적인 근거는 원칙 쪽이다** — 통짜로 담으면 §12 자신의 기준("simple enough for a coding agent to inspect and modify")이 깨지고, §24.2의 증분 수정("2km를 3km로")을 위해 ANA가 1.4MB 파일을 통째로 읽고 다시 써야 한다. 따라서 권고를 "최적화" 각도가 아니라 **"원칙 2·§12 준수 요건"** 각도로 썼다(그래야 "최적화는 나중에" 반론에 흔들리지 않는다). state에는 `resultRef`·`resultVersion`·`featureCount` 참조만 두고 피처 본문은 별도 엔드포인트 → 폴링 페이로드 2.4KB(596배 축소). gis가 이 구조를 **GIS-028(major, §12 `layers` 스키마 미정의)**로 별도 발행했으므로 병합하지 말고 ANA-001과 인접 배치할 것.

**Q2 → ANA-006: `moveend`/`zoomend` 기준 300ms trailing 디바운스.**

연속 발화하는 것은 `move`/`zoom`이고 `moveend`/`zoomend`는 제스처 종료 시 1회만 오므로 드래그는 이미 이벤트 1개로 접힌다. 남는 버스트(휠 줌 연타·키보드 팬)가 300ms면 묶인다. 250ms 아래는 휠 줌 연타가 낱개로 새고, 1초 위는 이동 직후 새로고침·이탈 시 마지막 상태를 잃어 §15.4 "markers survive page refresh"가 불안정해진다(안전 구간 250~500ms). 함께 명시한 것: 디바운스는 **연속 제스처에만** 적용하고 레이어 토글·피처 선택·마커 생성 같은 이산 액션은 즉시 쓰기, 그리고 동일 300ms를 Overpass 재질의 훅(GIS-003)에 재사용해 "뷰포트 변경 1회 = state 쓰기 1회 = 외부 질의 1회"로 정렬.

**정합성 축 결정 — 뷰포트 공유 의미론 (gis가 넘긴 설계 질문)**

뷰포트를 서버 공유하면 A 기기가 B 기기의 지도를 끌고 간다는 문제. **뷰포트 상태를 두 키로 분리하는 것으로 결정했다.**

- `map.view` — ANA가 설정하는 권위 있는 뷰포트. 변경 시 모든 클라이언트가 적용한다. §15.3 `"Move the map to Daejeon."`이 실제로 화면을 움직이려면 이 경로가 반드시 필요하며 이것이 Watch 루프의 핵심이다.
- `map.observedView` — 각 클라이언트가 자기 뷰포트를 보고하는 읽기 전용 슬롯. ANA의 §24.1 "current viewport" 조회를 만족시키되 **클라이언트는 이 값을 적용하지 않는다.**

이렇게 하면 B3의 서버 저장 규칙(localStorage 금지)을 지키면서 "한 사람의 화면이 다른 화면을 끌고 가는" 체감을 피할 수 있다. 어느 쪽을 택하든 **공유 여부가 의도된 동작임을 PRD 본문에 명시**해야 한다 — 명시가 없으면 앱마다 갈린다. 셀프호스팅 단일 사용자·다기기가 기본 전제이므로 `observedView`는 last-writer-wins로 충분하다.

**구조 축이 겹치지 않는다고 확인한 것**: §8.1(STR-029는 파일 목록 형식 불일치 — ANA-002의 런타임 계약 누락과 무관), §10.2(구조 축 발행 finding 없음 — ANA-009 단독).
